# 공통 시간이 없을 때의 복구 모델

2026-09-12. 사용자 채택 방향. 2026-09-13 상세 기획 기준 보강. 구현 완료·사용자 효과 검증·포트폴리오 수록 확정과 구분한다.

## 문서의 역할

이 문서는 첫 조율 뒤 공통 시간이 없을 때 MeetCue가 무엇을 계산하고, 무엇을 사람의 판단으로 남기며, 어떤 상태를 끝까지 이어야 하는지를 정의하는 제품 기획 기준이다. 초기 `CoordinationRecovery` 시안을 정당화하는 문서가 아니며, 이후 `ConstraintRecovery` 구현 기록과도 역할을 구분한다.

- 이 문서: 문제 정의, 계산 경계, Recovery Path 의미, 화면이 설명해야 할 정보, 성공·반증 기준.
- 구현 기록: 실제로 만든 상태 전이, UI, 테스트와 기술적 한계. [응답에서 계산하는 복구 경로](../design/constraint-recovery-2026-09-13/README.md).
- 결정 이력: 방향 채택과 변경 이유. [D-011·D-012](../process/decision-log.md#d-011--공통-시간이-없는-상황의-복구-모델을-중심-방향으로-채택).

대표 진입 상황은 **모든 필수 응답을 확인했지만 현재 조건으로 `ready` 후보가 하나도 없는 회의**다. 미응답 한 명의 답만 받으면 해결되는 상황은 기존 `pending` 흐름으로 다루며 이 기획의 대표 문제로 사용하지 않는다.

## 중심 원칙

**계산은 제품이 하고, 사회적 판단은 사람이 한다.**

모두의 응답을 확인해도 현재 조건으로 성립하는 후보가 없을 때, 어떤 명시적 조건이 달라지면 회의가 성립하는지 설명한다. 주최자가 복구 경로를 선택하고 필요한 당사자의 동의를 받은 뒤 확정한다. AI 최적 후보 추천은 중심 기능에 넣지 않는다. 문구 초안·요약 등 보조 기능은 별도 검토이며 구현 결정은 없다.

사용자가 제시한 국내 제품별 포지셔닝은 방향 제안의 맥락이다. 이번 기록에서는 각 제품의 최신 기능을 독립 검증하지 않았다. 경쟁사가 복구 기능을 제공하지 않는다거나 시장에 없는 기능이라는 주장으로 전환하지 않는다.

## 사용자가 답할 수 있어야 하는 질문

복구 화면을 본 주최자는 다음을 구분할 수 있어야 한다.

1. 왜 지금 바로 확정할 수 없는가?
2. 현재 조건 안에서 살릴 수 있는 후보는 무엇인가?
3. 각 후보가 성립하려면 누구의 어떤 동의가 필요한가?
4. 아직 모르는 정보와 이미 알려진 충돌은 어떻게 다른가?
5. 한 경로가 실패해도 어떤 기존 응답과 다른 후보가 유지되는가?
6. 현재 후보로 더 진행하지 않는다면 범위를 넓히거나 조율을 끝낼 수 있는가?

제품은 이 질문에 필요한 사실을 정리하지만, 어떤 사람에게 양보를 요구하는 것이 조직적으로 더 적절한지까지 대신 결정하지 않는다.

## 계산의 경계

- ‘미응답’은 불가가 아니다. ‘응답을 더 받으면 성립 여부를 알 수 있음’과 ‘알려진 충돌을 바꿔야 성립함’을 분리한다. 모든 응답을 확인했다는 사례에 미응답을 섞지 않는다.
- 현재 참석 조건을 그대로 적용한다. 선택 참석자의 불참만으로 성립 가능한 후보를 실패로 표시하지 않는다. 전원 참석은 별도 희망일 수 있으나 필수 기준과 섞지 않는다.
- 변경 요청은 당사자가 조정 의향을 밝힌 조건만을 대상으로 한다. 명시적인 변경 불가는 추천 경로에서 제외한다. 일정이 보인다는 이유로 이동 가능하다고 추측하지 않는다.
- 경로에는 필요한 사람, 필요한 동의, 일정 변경 건수, 알려진 제약, 아직 모르는 내용을 표시한다. 한 명이 여러 일정을 바꿀 수도 있으므로 사람 수와 변경 건수를 구분한다.
- ‘동의 1명’이 ‘동의 2명’보다 사회적 비용이 낮다고 단정하지 않는다. 점수·성공 확률·최적 순위로 환산하지 않는다. 날짜·시간을 바꾸는 것이 업무 중요도보다 낫다고 결정하지 않는다.
- 조정 의향은 변경 동의가 아니다. 요청 단계에서도 ‘확정 가능’ 대신 ‘동의하면 성립’을 사용한다. 필요한 동의가 모두 들어오면 주최자가 확정한다.
- 기존 답은 같은 후보와 유효한 조건에 대해서만 재사용한다. 새 시간에 이전 답을 복사하지 않는다. 변경 동의는 요청한 후보에 묶고 다른 후보로 전용하지 않는다.

## Recovery Path의 정의

기존 MeetCue의 중심 객체가 후보와 `ready / pending / impossible` 판정이었다면, 복구에서는 **Recovery Path**를 함께 다룬다.

Recovery Path는 현재 성립하지 않는 후보를 성립 상태까지 가져가기 위해 **추가로 확인되어야 하는 명시적 조건의 집합**이다. 단순히 사람이 몇 명 부족한지 세는 값이 아니다.

경로에는 최소한 다음 정보가 필요하다.

- 후보 날짜와 시간
- 현재 성립하지 않는 이유
- 필요한 사람과 필수/선택 여부
- 각 사람이 이미 밝힌 상태: `unknown`, `adjustment intent`, `unavailable` 등
- 새로 필요한 확인 또는 동의의 종류
- 영향을 받는 사람 수와 알려진 일정 변경 건수
- 그대로 유지할 수 있는 동일 후보의 기존 응답
- 요청 상태: 요청 전 / 대기 / 일부 동의 / 전원 동의 / 거절 / 취소 / 종료
- 경로가 더 이상 유효하지 않다면 그 이유

### 행동 유형

Recovery V1에서 행동의 의미를 다음처럼 구분한다.

#### 1. 추가 응답 확인

아직 해당 후보를 확인하지 않은 사람이 있고 그 응답에 따라 성립 여부가 달라진다면 기존 `pending` 흐름의 대상이다. 복구 모델은 이 상태를 계산할 수 있지만, **전원 응답 후 공통 시간이 없는 대표 사례와 섞지 않는다.**

#### 2. 변경 동의 확인

당사자가 해당 후보에 대해 이미 `일정을 조정하면 참석 가능`이라는 의향을 밝혔고, 실제로 기존 일정을 옮길 동의가 아직 없는 경우다.

> 민수님의 일정 변경 동의가 있으면 이 후보가 성립해요.

의향은 동의로 승격하지 않는다. 당사자가 요청한 후보에 명시적으로 동의해야 한다.

#### 3. 여러 사람의 변경 동의 확인

한 후보에 둘 이상의 명시적 변경 동의가 필요한 경우다. 사람 수와 일정 건수를 함께 보여주되 이를 사회적 비용 점수로 환산하지 않는다. 같은 후보 안에서는 필요한 당사자들에게 함께 확인할 수 있지만 일부 동의만으로 확정하지 않는다.

#### 4. 현재 조건으로 복구 불가

필수 참석자가 명시적으로 변경 불가라고 답했거나 현재 규칙으로 성립시킬 수 없는 후보는 **재확인 추천 경로로 만들지 않는다.** 사용자가 이미 밝힌 불가를 단순 미확인처럼 다시 묻지 않는다.

> 수진님의 외근은 변경하기 어렵다고 확인됐어요. 이 후보는 현재 조건으로 진행하지 않아요.

회의 조건 자체를 바꾸거나 당사자와 제품 밖에서 새로 협의하는 것은 별도 결정이다.

#### 5. 범위 확장 또는 종료

현재 후보의 복구 경로가 모두 닫혔거나 주최자가 기존 경로를 선택하지 않으면 시간 범위를 넓히거나 조율을 끝낼 수 있다. 범위를 넓혔다고 이전 후보의 답을 새 후보의 답으로 복사하지 않는다. 대신 **과거 후보에서 확인한 기록은 이력으로 유지하고 새 후보에서 실제로 필요한 응답만 새로 수집한다.**

## 경로 비교 원칙

제품은 `동의 1명`, `동의 2명`, `일정 1건` 같은 조건을 보여줄 수 있지만, 이를 하나의 부담 점수로 합산하지 않는다.

사용자가 비교할 수 있는 사실은 예를 들어 다음과 같다.

- 변경 동의가 필요한 사람 수
- 알려진 일정 변경 건수
- 이미 조정 의향을 밝힌 사람인지
- 명시적인 변경 불가 때문에 닫힌 후보인지
- 해당 후보에서 그대로 유지되는 기존 응답 수
- 아직 확인되지 않아 판단 자체가 불가능한 정보가 있는지

따라서 `최적`, `성공 확률 92%`, `AI 추천 1순위`처럼 사회적 판단을 압축한 라벨을 기본값으로 사용하지 않는다. 정렬이 필요하면 확정 가능성·요청 진행 상태처럼 명시적인 제품 상태를 우선하고, 변경 인원만으로 사람 사이의 부담을 서열화하지 않는다.

## 끝까지 구현할 단일 사례

아래는 설계 검토용 가상 사례이며 실제 조율 기록이 아니다. 실제 사례를 확보하면 재구성·대조한다.

6명, 다음 주 1시간, 지훈·수진·민수·서연 필수, 도윤·유나 선택. 모든 사람이 아래 세 후보에 답했다. 현재 성립하는 후보는 없다.

| 후보 | 현재 충돌 | 당사자가 밝힌 조건 | 제품이 설명할 경로 |
| --- | --- | --- | --- |
| 화 14시 | 필수 민수의 기존 일정 1건 | 조정해 볼 의향 있음, 아직 동의하지 않음 | 민수 1명의 일정 변경 동의가 필요 |
| 목 16시 | 필수 수진·서연의 기존 일정 각 1건 | 두 사람 모두 조정 의향 있음, 아직 동의하지 않음 | 2명에게 각각 변경 동의가 필요 |
| 금 10시 | 필수 수진의 외근 | 시간 변경 불가 | 현재 조건으로 복구 불가. 변경 요청 대상으로 삼지 않음 |

각 후보의 나머지 사람은 가능하다고 답했다. 두 경로의 숫자는 관찰된 부담의 객관 점수가 아닌 조건 수다.

### 핵심 분기

1. 주최자는 화요일의 1명 변경과 목요일의 2명 변경을 비교한다. 제품은 숫자만으로 하나를 최적으로 지정하지 않는다.
2. 화요일을 선택해 민수에게 요청한다. 민수가 거절하면 화요일은 닫히며 다른 후보에 대한 답은 유지된다. 같은 거절에 반복 양보를 요청하지 않는다.
3. 목요일로 이동하면 수진·서연의 명시적 동의가 모두 필요하다. 한 명의 수락만으로 확정하지 않는다. 동일 경로의 두 사람에게 함께 확인할 수 있게 하되, 두 후보에 대한 변경 약속을 동시에 추진하지 않는다. 이 운영 방식의 지연 비용은 별도 검토한다.
4. 두 명 모두 동의하면 주최자가 확정한다. 기존 캘린더 일정을 자동으로 옮겼다고 주장하지 않는다.
5. 한 명이 거절하면 그 경로도 닫힌다. 다른 사람의 이미 받은 동의는 기록에 남기되 ‘이 후보로 진행하지 않음’을 알리고, 실제 일정 변경 전에 최종 확정을 기다리도록 한다. 제품 밖에서 이미 실행한 변경을 자동 복구했다고 표현하지 않는다.
6. 남은 경로가 없으면 ‘현재 범위와 조건에서는 성립하지 않음’을 보여준다. 주최자가 범위를 바꾸거나 조율을 종료하도록 한다. 필수 참석자를 몰래 제외하거나 시간을 임의로 줄이지 않는다. 범위를 바꾸면 새 후보에 필요한 답을 다시 받고, 과거 후보의 기록은 유지한다.

## 화면별 정보 요구사항

구체적인 레이아웃은 디자인 단계에서 바꿀 수 있지만, 아래 의미는 유지한다. 화면 수 자체가 요구사항은 아니다.

### 1. 복구 경로 비교

대표 화면이다. `가능한 시간이 없음`에서 끝내지 않고 **현재 조건에서 어떤 경로가 남아 있는지**를 비교할 수 있어야 한다.

상단은 다음 사실을 먼저 말한다.

> 바로 확정할 수 있는 시간은 없어요. 받은 응답을 유지한 채 조율을 이어갈 수 있어요.

각 후보에서는 최소한 다음을 보여준다.

- 날짜·시간
- 왜 현재 성립하지 않는지
- 필요한 동의 대상과 수
- 당사자가 이전에 밝힌 조정 의향 또는 변경 불가
- 같은 후보에서 다시 묻지 않아도 되는 응답
- 요청 가능 / 요청 중 / 일부 동의 / 닫힘 상태

파란 CTA나 추천 배지로 근거 없이 한 후보를 답처럼 만들지 않는다.

### 2. 요청 전 확인

주최자가 경로를 선택하면 누구에게 무엇을 요청하는지, 그 요청이 받아들여졌을 때 무엇이 달라지는지 확인한다.

예:

> 민수님이 이 변경에 동의하면 다른 5명의 응답을 다시 받지 않고 화요일 후보를 확정할 수 있어요.

기존 캘린더 일정을 MeetCue가 자동으로 옮기지 않는다는 경계를 함께 보여준다.

### 3. 당사자의 명시적 동의

참석자는 과거의 `조정 의향`을 실제 `변경 동의`로 바꾸는 질문을 받는다. 해당 후보와 알려진 충돌을 함께 보고 무엇에 동의하는지 이해할 수 있어야 한다.

- 동의: 이 후보로 회의를 정해도 된다는 명시적 의사 표현
- 거절: 기존 일정을 유지하며 이 후보는 진행하지 않음

동의해도 기존 캘린더 이벤트가 자동 수정된다고 표현하지 않는다.

### 4. 응답 반영과 재계산

수락이면 필요한 모든 동의가 들어왔는지 다시 계산한다. 부분 동의만으로 확정 버튼을 열지 않는다.

거절이면 해당 경로를 닫고 다른 후보의 기존 답을 유지한 채 남은 경로를 다시 보여준다.

먼저 동의한 사람이 있는 경로에서 다른 당사자가 거절했다면, 먼저 동의한 사람의 기록은 남기되 **그 후보로 진행하지 않는다는 상태**도 분명히 한다.

### 5. 범위 확장 또는 조율 종료

모든 경로가 닫히면 이를 오류가 아니라 정상적인 결과로 보여준다.

> 현재 범위와 조건에서는 회의를 성립시키기 어려워요.

주최자는 새 시간을 제안하거나 확정 없이 종료할 수 있다. 새 후보는 기존 후보의 응답을 자동 복사하지 않으며, 새 후보에 필요한 사람에게만 새 응답을 요청한다.

## 상태 보존 원칙

- 한 후보의 거절은 다른 후보의 응답을 삭제하지 않는다.
- 한 후보의 변경 동의는 다른 후보에 적용하지 않는다.
- 요청 취소 뒤 늦게 도착한 답은 현재 요청의 유효한 동의로 사용하지 않는다.
- 여러 사람의 동의가 필요한 경로는 전원이 동의하기 전까지 미완료다.
- 일부 동의 뒤 경로가 닫혀도 누가 무엇에 동의했었는지는 이력으로 보존한다.
- 범위를 넓힌 뒤 새 후보는 새 판단 대상이다. 과거 후보의 `가능`을 그대로 전용하지 않는다.

이 원칙의 목적은 가능한 많은 정보를 재사용하는 것이 아니라 **확인한 의미의 범위를 넘어서 추론하지 않는 것**이다.

## 완료 기준

- 두 후보에 고정된 현재 시안 상태 대신 참석자·후보·응답에서 경로를 도출한다.
- 미응답, 변경 의향, 동의, 거절을 다른 상태로 계산한다.
- 1명 거절 → 2명 동의 경로 → 부분 수락 → 전원 동의 → 주최자 확정이 연결된다.
- 부분 수락 뒤 거절·늦은 응답·요청 취소가 잘못된 확정으로 이어지지 않는다.
- 모든 경로 실패를 정상 결과로 표현하고 새 범위 또는 종료로 연결한다.
- 화면을 늘린 수가 아닌, 위 분기를 이해하고 판단할 수 있는지로 검토한다. 구현 테스트는 사용자 효과의 증거가 아니다.

## 사용자 검증에서 확인할 것

기능 테스트와 별도로, 주최자가 대표 화면을 보고 다음을 정확히 설명할 수 있는지 확인한다.

1. 왜 현재 바로 확정할 수 없는가?
2. 화요일과 목요일 경로는 각각 어떤 사람의 어떤 동의가 필요한가?
3. `조정해 볼 의향`과 `이미 변경에 동의함`은 어떻게 다른가?
4. 금요일 후보는 왜 요청 경로가 없는가?
5. 일부만 동의했을 때 왜 아직 확정할 수 없는가?
6. 한 경로가 거절되어도 어떤 정보가 남는가?
7. 모든 경로가 실패하면 무엇을 할 수 있는가?

정확한 이해 기준과 참여자 수는 실제 검증 계획에서 별도로 정한다. 현재 구현 테스트 통과를 이 질문들의 사용자 이해 증거로 대체하지 않는다.

## 반증·재검토 조건

다음이 관찰되면 문제 정의나 표현을 다시 검토한다.

- 주최자가 복구 경로 비교보다 기존 후보표를 직접 읽는 편을 더 쉽고 빠르게 느낀다.
- 실제 일정 조율에서는 공통 시간이 없을 때 기존 후보를 살리기보다 즉시 새 범위를 잡는 경우가 대부분이다.
- `일정을 조정하면 가능` 응답이 사용자에게 이미 확정 동의와 동일한 의미로 받아들여져 별도 동의 단계가 불필요하다.
- 사람 수·일정 건수 표시가 특정 사람에게 반복적으로 양보를 요구하는 사실상의 추천으로 읽힌다.
- 새 범위를 탐색할 때 기존 정보의 의미 범위가 좁아 대부분을 다시 물어야 하며, 누적되는 조율 기록의 효용이 작다.
- 여러 사람에게 같은 후보의 동의를 함께 요청하는 방식이 지연·혼선·취소 비용을 키워 순차 요청이나 다른 운영 방식이 더 낫다.

## AI 사용 원칙

Recovery Path의 성립 조건과 동의 상태는 명시적인 도메인 규칙으로 계산한다. AI가 `가장 적절한 사람`, `가장 희생이 적은 일정`, `최적 후보`를 대신 판단하지 않는다.

후속 검토 가능한 AI 역할은 요청 문구 초안, 긴 사유의 요약, 계산된 경로의 자연어 설명처럼 **판단 결과를 바꾸지 않는 보조 레이어**다. AI 사용 여부는 이 핵심 복구 모델의 완성 조건이 아니다.

## 포트폴리오에서 보여줄 수 있는 판단

사용자 효과가 검증되기 전에는 `기존 제품보다 우수하다`, `조율 시간을 줄였다`, `시장에 없는 기능이다`라고 주장하지 않는다.

현재 보여줄 수 있는 것은 다음 설계 변화다.

> 일정 조율 실패를 `다른 시간을 다시 찾는 문제`로만 보지 않고, 이미 확보한 응답 위에서 **어떤 명시적 조건이 달라져야 성립하는지와 그 판단 경계**를 구조화했다.

이때 핵심은 Recovery Path라는 이름 자체가 아니라, 자동화할 수 있는 계산과 사람이 해야 하는 사회적 판단을 분리한 과정이다.

2026-09-12의 초기 `CoordinationRecovery` 시안은 이 목표에 미달했다. 해당 시안은 폐기한 역사로 덮어쓰지 않고, 한 명의 확인만 남은 초기 탐색으로 보존한다.

## 2026-09-13 구현 후속

위 마지막 평가는 2026-09-12 초기 시안에 대한 기록이다. 이후 별도 계산 모델과 `ConstraintRecovery`를 개발용 recovery 경로에 연결했다. 응답 기반 경로 도출, 부분 동의 차단, 요청별 이력, 거절 이후 다른 경로, 새 후보의 재확인과 종료를 구현·검수했다. [구현과 검수 범위](../design/constraint-recovery-2026-09-13/README.md). 실제 사용자 효과·서비스 통합·포트폴리오 수록은 아직 확인하지 않았다.
