# 개선 과정과 포트폴리오 검토 기록

2026-09-12 시작. 목적은 과정을 보존하고, 나중에 어떤 판단을 포트폴리오에 사용할지 검토할 수 있게 하는 것이다. 지금 포트폴리오 수록을 결정하거나 과거 제출물을 다시 쓰는 문서가 아니다.

## 읽는 순서

1. [판단 기록](decision-log.md): 개선 관점, 시도·보류·대체한 안, 근거와 미검증 사항.
2. 각 기록의 원문·시안·검증 링크: 당시 자료를 확인한다. 기록 요약이 원본을 대신하지 않는다.
3. [기록 양식](entry-template.md): 새 작업에서 같은 구조로 이어 쓴다.

## 기록 원칙

- 큰 흐름·재질·입력 방식·문제 정의를 바꿀 때 남긴다. 모든 CSS 수정이나 커밋을 이야기로 만들지는 않는다.
- 작업 전 문제와 대안을 쓰고, 작업 후 구현·검증·남은 의문을 덧붙인다. 당시 기록이 없는 과거 판단은 ‘후일 재구성’으로 표시한다.
- `제안 / 비교 중 / 채택 / 구현 기록 있음 / 보류 / 대체됨 / 폐기`를 구분한다. 구현 기록이 있어도 사용자 효과가 검증됐다는 뜻은 아니다. 현재 코드와의 일치 여부도 별도 확인한다.
- 상태를 바꿀 때 이전 판단은 지우지 않고 날짜·이유·후속 기록을 추가한다. 재검토 조건을 함께 쓴다.
- 스크린샷은 가능하면 같은 시나리오·뷰포트로 전후를 보존한다. 경로, 날짜, 데이터 조건을 적고 다르면 비교 한계를 적는다. 캡처를 못 했으면 없음으로 남긴다.
- 공개 사례와 사용자 테스트, 실제 측정과 가상 시나리오를 구분한다. 수치가 없으면 비워 두며 소급해서 만들어 넣지 않는다.
- 무드보드는 디자인 의도를 설명하는 참고다. 원본 제작자·사용 권리가 확인되지 않은 이미지는 포트폴리오 공개 전에 출처와 사용 범위를 검토한다.

## 나중에 수록을 검토하는 기준

| 확인할 것 | 검토 질문 |
| --- | --- |
| 문제와 연결 | 화면이 달라진 이유를 구체적인 조율 상황으로 설명할 수 있는가? |
| 선택의 이유 | 실제로 고려한 대안과 감수한 비용이 있는가? |
| 증거 수준 | 관찰·피드백·가설·기능 확인 중 무엇인지 정직하게 표시했는가? |
| 결과 | 개선 효과 또는 실패를 뒷받침하는 자료가 있는가? 없으면 탐색 과정으로 설명 가능한가? |
| 개인의 기여 | 사용자가 판단한 부분과 AI·개발 도구가 수행한 부분을 구분할 수 있는가? |
| 전달 가치 | 기능 목록이나 시안 나열보다 판단력을 보여주는가? 다른 프로젝트와 역할이 겹치지 않는가? |
| 공개 가능성 | 당시 제출물과 사후 개선을 구분했는가? 개인정보·레퍼런스 출처를 확인했는가? |

수록 상태는 `미정 / 검토 후보 / 근거 보강 필요 / 제외 / 수록 확정`으로 기록한다. ‘검토 후보’는 공개 승인이 아니다. 실제 사용자 연구가 없어도 탐색으로 소개할 수 있지만 효과가 입증됐다고 표현하지 않는다.
