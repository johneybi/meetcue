# MeetCue 답변 보강 초안 v9

작성 기준: 2026-09-07 회고와 현재 프로토타입 수정. 실제 사용자 검증 전의 설명 초안이며, 과거 제출본이나 재지원 완료본이 아니다. 질문은 제공받은 회고용 v8에 적힌 문구를 따른다. 제출 글자 수 제한은 별도 확인이 필요하다.

참고: 당시 답변 후보 `review-source-v6.md`와 회고 초안 `draft-v8.md`. 실제 사용자 관찰 없이 ‘발견했다’, ‘검증했다’, ‘시간을 줄였다’라는 성과를 만들지 않는다.

## Q1. 사용자의 어떤 문제를 발견했나요? 그것이 왜 문제라고 생각했나요?

과제의 여섯 명 일정에서, 참석 가능한 사람이 많다는 사실과 회의를 열 수 있다는 조건이 다를 수 있다는 점에 주목했습니다. 다섯 명이 가능해도 필수 참석자가 빠지면 다른 시간이 필요하고, 반대로 필수 참석자와 최소 인원이 모였다면 선택 참석자의 답을 더 기다리지 않아도 됩니다. 저는 일부 응답이 남았을 때 주최자가 이 조건을 다시 계산하고 다음 행동을 정해야 하는 일을 해결 대상으로 삼았습니다. 잘못 해석하면 꼭 필요한 사람이 빠진 시간을 고르거나, 이미 가능한 시간이 있는데도 결정을 미룰 수 있기 때문입니다. 다만 이것은 과제 조건에서 도출한 가설입니다. 실제 사용자의 가장 큰 불편이라고 확인한 것은 아니며, 응답을 받는 수고와 결과를 판단하는 수고 중 어디에 더 큰 부담이 있는지 비교할 필요가 있습니다.

## Q2. 그 문제를 어떻게 해결했나요?

필수 참석자와 최소 인원을 기준으로 각 시간을 지금 정할 수 있는지, 추가 응답이 필요한지, 다른 시간을 찾아야 하는지 보여주도록 만들었습니다. 선택한 시간이 대기 중이어도 이미 가능한 다른 시간이 있다면 먼저 이동할 수 있게 했습니다. 특정 후보가 꼭 필요한 경우에는 누구의 답을 더 받아야 하는지 확인하고 요청할 수 있습니다. 참석자는 캘린더로 채운 초안에서 실제 일정과 다른 칸을 고칩니다. 응답 상태를 먼저 고르고 시간에 적용하게 했고, ‘옮겨서 참석해요’를 선택하면 해당 시간으로 확정될 때 일정을 옮겨 참석한다는 의미를 저장 전에 다시 확인합니다. 새 응답 후에는 같은 후보의 인원과 근거가 어떻게 달라졌는지 확인할 수 있습니다. 이 동작은 프로토타입으로 구현했으며, 이해도와 작업 시간의 개선은 아직 측정하지 않았습니다.

## Q3. 왜 이 방식으로 설계했나요?

처음에는 후보 3~5개에 답하는 방식을 검토했습니다. 후보가 이미 좁혀진 회의라면 그 방식이 더 간단할 수 있습니다. 반면 처음 후보가 모두 맞지 않으면 새로운 시간을 다시 물어야 합니다. 저는 캘린더가 충분히 기록되어 있고 재조율이 필요한 상황을 가정해, 범위의 예외를 수정하고 제품이 후보를 계산하는 방식을 구현했습니다. 가능한 시간을 더 찾는 이익이 넓은 시간표를 검토하는 비용보다 크다는 점은 아직 검증하지 못했습니다. 따라서 제품은 필수 조건과 인원을 계산하되, 관계와 회의 중요도를 고려한 최종 선택은 주최자에게 남겼습니다. 일정 이동도 자동으로 추정하지 않고 참석자가 직접 약속하게 했습니다. 현재는 후보 입력이 유리한 상황과 범위 입력이 유리한 상황을 나눠 비교할 준비를 했으며, 결과에 따라 입력 범위나 시작 방식을 바꿀 계획입니다. 실제 캘린더 연동과 알림 발송은 구현 범위에서 제외했습니다.
