# MeetCue 비교 검증 진행안

> 구현 버전 주의: 2026-09-07 제품 개선 이후 B는 ‘세 후보 먼저 응답 → 필요하면 전체 시간표’ 흐름이다. 아래의 전체 시간표를 바로 여는 진행문은 [v3](../product/progressive-response-v3.md)에 맞춰 조정하고, 관찰 시 사용한 커밋 또는 빌드를 기록해야 한다. 기존 빈 관찰표를 실제 테스트 결과로 해석하지 않는다.

상태: 실행 준비 완료 / 실제 참가자 검증 미수행. 아래 상황과 데이터는 비교를 위한 가상 자극이며 실제 고객 사례가 아니다.

## 무엇을 분리해서 확인하는가

두 결정을 한꺼번에 비교하면 무엇이 효과를 냈는지 알기 어렵다.

1. **입력 방식:** 후보 3개에 답하기 vs 캘린더를 검토해 시간 범위 수정하기.
2. **결과 해석:** 사람별 응답표 vs 같은 응답에 기준 충족 여부·다음 행동을 붙인 화면.

1차는 업무 회의 조율 경험자 5명에게 개별 관찰을 진행한다. 인당 25–35분을 예상하되 실제 소요는 기록한다. 선호 투표나 통계적 우위 검증이 목적이 아니다. 같은 사람이 주최자·참석자 역할을 번갈아 하면 역할 시뮬레이션이며 실제 6명 협업 결과로 보고하지 않는다.

후속으로 실제 주최자 1명과 초대자 5명이 조율할 때 총 작업 시간을 측정한다. 총 작업 시간은 주최자 설정·판단 시간 + 다섯 참석자의 실제 입력·수정 시간 합이다. 한 사람의 시간을 5배해 실제 총량으로 제시하지 않는다. 응답 대기 시간은 별도 측정한다.

## 준비

- 두 방식 모두 같은 캘린더와 회의 조건을 볼 수 있게 한다. 후보 방식에서 캘린더를 숨겨 MeetCue에 유리하게 만들지 않는다.
- 캘린더 정상 기록 상황과 누락 상황을 둘 다 준비한다. 연동·로그인 시간은 별도 기록한다. 현재 MeetCue는 연동 완료를 가정한 프로토타입이므로 실제 연동 비용을 비교한 것으로 보고하지 않는다.
- 참가자에게 개선 이유나 정답을 설명하지 않는다. 시간 측정 중에는 생각을 말하도록 요구하지 않고, 완료 뒤 설명을 듣는다.
- P01·P03·P05는 후보 → 범위, P02·P04는 범위 → 후보 순으로 수행한다. 두 번째 과제는 날짜·이름을 바꾼 동형 데이터로 학습 효과를 줄인다. 완전히 제거한 것으로 해석하지 않는다.
- PC와 모바일 결과를 한 묶음의 속도 수치로 합치지 않는다. 기기·입력 방법·화면 크기를 기록한다.
- 제품 수정 전 비교는 Git의 이전 버전을 별도 checkout에서 실행하거나 보존한 화면을 쓴다. 화면만 비교했다면 클릭 수·입력 속도 개선을 측정했다고 기록하지 않는다.

## 입력 비교: 바로 쓸 수 있는 역할 카드

공통 조건: 주최자를 포함한 6명, 1시간 회의. 날짜 1·2·3은 실행 시 조율 범위의 앞 세 날짜로 바꾼다. 두 방식의 시간 범위는 10:00–12:00, 13:00–17:00으로 맞춘다. 현재 데모 범위가 다르면 먼저 동일 범위의 테스트 회의를 생성한다. 정확히 맞추지 못하면 이 입력 비교는 진행하지 않는다.

**참석자에게 읽어줄 과제:**

> 이 기간에 회의에 참석할 수 있는 시간을 알려주세요. 아래 캘린더와 별도 메모가 본인의 실제 일정입니다. 기존 일정을 옮기겠다고 답한 시간은 회의가 확정되면 직접 옮겨 참석해야 합니다. 요청을 마칠 수 있다고 생각하면 저장해 주세요.

| 날짜   | 캘린더 일정                                      | 캘린더 밖 메모                                       |
| ------ | ------------------------------------------------ | ---------------------------------------------------- |
| 날짜 1 | 10–11시 팀 회의, 14–15시 리뷰                    | 리뷰는 다른 사람과 협의 전이라 이동 가능 여부를 모름 |
| 날짜 2 | 10–11시 팀 회의, 13–14시 공유, 15–16시 개인 작업 | 개인 작업은 본인이 확실히 옮길 수 있음               |
| 날짜 3 | 10–11시 1:1, 13–14시 리뷰                        | 15–17시 외근. 누락 조건에서는 캘린더에 기록되지 않음 |

**A — 후보 응답지:** 다음 세 후보 각각에 가능 / 일정을 옮겨 참석 / 불가를 고르게 한다. 화면 또는 종이 여부를 기록한다. 종이를 썼다면 디지털 UI 속도 비교로 해석하지 않는다.

| 후보 | 시간            | 응답 |
| ---- | --------------- | ---- |
| A1   | 날짜 1, 11–12시 |      |
| A2   | 날짜 2, 15–16시 |      |
| A3   | 날짜 3, 15–16시 |      |

**B — 범위 응답지:** 같은 캘린더와 메모를 보며 MeetCue의 동일 범위를 검토·수정하고 저장한다. 칸 하나의 상태를 여러 번 바꾸는지, 선택한 도구를 잊는지, 날짜를 놓치는지 기록한다.

**진행자 정답:** A1 가능, A2 옮겨서 참석, A3 불가. 범위에서는 날짜 1의 리뷰를 확약하면 안 된다. 캘린더 누락 조건에서는 날짜 3 외근 4칸이 가능으로 남으면 오류다.

**두 가지 후속 상황을 모두 제시한다:**

- S1: 다른 동료의 응답을 합치니 A1에 회의 기준이 충족된다. 여기서 작업을 종료한다. 후보 방식이 유리할 수 있는 정상 사례다.
- S2: 세 후보 모두 필수 참석자와 맞지 않는다. 날짜 2의 11–12시에는 기준을 충족할 가능성이 있다. A는 새 후보를 물을 수 있고 B는 이미 받은 범위에서 찾을 수 있다. 추가 입력·메시지·전환을 기록한다. 이 상황을 만들었다고 재조율이 실제로 자주 발생한다는 증거가 되지는 않는다.

입력 완료 시간만 비교하지 않는다. A와 B가 수집한 정보량이 다르므로 S1/S2 각각에서 적절한 시간에 도달하기까지의 후속 작업도 포함한다. 종이 A vs 실제 앱 B라면 사용성 관찰까지만 하고 순수한 구현 속도 비교 결론은 보류한다.

## 결과 해석 비교: 독립된 표 과제

역할: 민지가 주최자. 민지·민수·서연은 필수, 주최자 포함 최소 4명. 준호·수진·하나는 선택. 일정 조정을 확약한 사람은 가능 인원에 포함한다.

### R1 — 이미 정할 수 있는데 기다리는가?

| 사람 | 역할        | 시간 A | 시간 B |
| ---- | ----------- | ------ | ------ |
| 민지 | 필수·주최자 | 가능   | 가능   |
| 민수 | 필수        | 가능   | 가능   |
| 서연 | 필수        | 가능   | 가능   |
| 준호 | 선택        | 가능   | 불가   |
| 수진 | 선택        | 미응답 | 미응답 |
| 하나 | 선택        | 가능   | 불가   |

요약 화면에 붙일 문장: A는 ‘5명 참석 가능, 지금 확정할 수 있어요’, B는 ‘수진님의 가능 응답이 필요해요’. B를 선택했을 때 A로 이동할 수 있어야 한다.

중립 질문: “회의 시간을 정하려고 합니다. 지금 어떤 행동을 하겠어요? 그 이유는 무엇인가요?”

판정: A는 바로 확정 가능하다. B를 선호한다는 추가 조건이 없는데 무조건 수진을 기다려야 한다고 해석하는지 관찰한다. 특정 시간을 선호한다는 자발적 이유는 기록하고 곧바로 오류로 단정하지 않는다.

### R2 — 추가 응답이 실제로 필요한가?

R1에서 준호의 시간 A를 불가, 하나의 시간 A를 불가, 민수의 시간 A를 불가로 바꾼다. B는 그대로 둔다. 이제 A는 필수 참석자 불가, B는 수진이 가능하면 최소 인원을 채운다. 진행자용 정답은 수진에게 B의 가능 여부를 확인하는 것이다. 준호·하나에게 미응답 재촉을 하면 안 된다.

### R3 — 새 응답으로 무엇이 바뀌는가?

R2의 수진이 B에 가능이라고 답한 표를 보여준다. B는 같은 시간·같은 필수 조건에서 3명 → 4명으로 바뀐다. “무엇이 바뀌었고 지금 무엇을 할 수 있나요?”라고 묻는다. 이름·시간을 바꿔 정답을 외우지 않은 동형 과제로 표와 요약 화면을 교차 비교한다.

현재 앱에서 R1 유사 사례는 데모 가이드 2번으로 볼 수 있다. R2/R3의 정확한 표는 위 자극으로 관찰하며, 앱과 같은 데이터가 아니면 앱의 속도 결과와 합치지 않는다. 화면 설명 자체의 비교와 실제 앱 동작 비교를 구분한다.

## 의미 확인 질문

과제 후, 먼저 참가자의 말로 설명하게 한다.

1. “‘옮겨서 참석해요’를 저장하면 주최자는 무엇을 해도 되나요?”
2. “기존 일정을 옮길 수 있을지 아직 모른다면 어떤 응답을 고르겠어요?”
3. “캘린더에 비어 있던 칸은 언제 다른 사람에게 전달되나요?”
4. “실제로 일정을 잡을 때 이 두 방식 중 각각 언제 쓰겠어요?”

정답 유도 질문인 “이게 더 편하죠?”는 쓰지 않는다. 저장 확인 문구를 읽었는지, 읽었어도 다르게 이해했는지를 분리한다.

## 기록과 의사결정

[관찰 CSV](comparison-observations.csv)에 한 사람·한 과제·한 방식당 한 행을 기록한다. 응답 시간은 과제 이해 후 첫 조작부터 완료 선언까지이며, 진행자가 도와준 시점과 내용은 별도 기록한다. 재확인 횟수는 이미 본 캘린더/표를 결정을 위해 다시 확인한 횟수다. 실제 발화만 인용하고 요약에는 요약임을 표시한다.

- **중대한 의미 오류:** 확약을 잠정 가능으로 이해하거나 필수 참석자 불가인 시간을 확정한다면, 발생 인원·맥락을 기록하고 설계를 다시 검토한다. 평균 시간이 빨라도 이 오류를 상쇄했다고 보지 않는다.
- **조건별 비용:** S1에서 후보 방식이 간단하고 S2에서 범위 방식이 유리하면, 사용자 실제 조율 경험에서 두 상황의 빈도를 별도로 조사한 뒤 기본 진입 방식을 정한다.
- **자동 채움 신뢰:** 외근 누락을 반복해서 놓치면 기본 가능 처리·검토 방식 변경을 우선한다.
- **검증 후 답변:** 관찰 인원, 과제, 실패, 수정 내용을 사실 그대로 추가한다. 소규모 시뮬레이션에서 얻은 시간 차이를 실제 업무 전체의 절감률로 발표하지 않는다.

아직 어떤 관찰 행도 채우지 않았다. 다음 산출물은 실제 관찰 결과와 그 결과로 바꾼 한 가지 설계 결정이다.
