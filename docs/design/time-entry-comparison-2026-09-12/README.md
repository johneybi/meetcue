# 시간 입력 비교안 · 2026-09-12

상태: 로컬 비교 프로토타입 구현·기능 검수 완료. 실제 사용자 비교 미실시. 사후 개선이며 원 채용 제출물에 포함됐던 작업이 아니다. 포트폴리오 수록은 미정이다.

## 무엇을 비교하는가

사용자는 기본 시간 입력을 먼저 정리하고, 같은 조건에서 대안을 비교하는 진행을 승인했다. 조사에서는 범위 입력과 날짜별 예외의 마찰을 확인했지만 특정 UI가 더 낫다는 효과는 확인되지 않았다.

- **A · 시간표 중심**: 기존 `AvailabilityWindowPicker` 그대로 사용. 평일 9–18시로 시작하며 드래그·직접 추가/제외·되돌리기를 제공한다. A도 제외 기능이 있으므로 ‘제외 있음 vs 없음’ 비교가 아니다.
- **B · 범위와 예외**: 날짜와 기본 시간대를 먼저 확인 → 예외를 제외 → 날짜별 남은 시간을 읽는다. 가능한 시간이 적으면 빈 범위에서 시작할 수 있다. 세밀한 수정은 기존 시간표를 펼쳐서 한다.
- 같은 버튼·선택 상태·모달·시간 계산을 재사용한다. 서비스 본 흐름을 B로 교체하지 않았다.

[비교 화면 열기](http://127.0.0.1:5173/meetcue/design-review.html?view=time-comparison). 개발 서버 전용 검토 페이지다. 현재 일반 프로덕션 빌드에는 design-review.html이 포함되지 않는다.

## 보존과 비교 조건

- [기존 서비스 검토 화면](01-existing-screen.png): 변경하지 않은 시간 선택 화면. 검토 도구에 비교 탭을 추가한 뒤 캡처했으므로 페이지 전체의 변경 전 캡처는 아니다.
- [A 최종 비교 화면](08-a-desktop-final.png) / [B 기본 범위 화면](07-b-desktop-base.png): 같은 ‘대부분 가능한 주’, 같은 기본 1280×720 뷰포트에서 전체 페이지 캡처. 문서 스크롤바로 실제 콘텐츠 폭은 1265px. A는 기본 범위를 이미 적용한 상태, B는 확인 전 상태다. 이 진입 단계의 차이도 비교 대상이다.
- [B 예외 적용 화면](03-b-exceptions.png): 기본 범위에서 점심과 화요일 예외를 뺀 상태. 비교 설정을 접기 전의 중간 구현 캡처다. 최종 A와 순수 시각 비교에 사용하지 않는다.
- [B 390px 기본 범위](04-b-mobile-base.png), [B 390px 입력창](05-b-mobile-entry.png), [B 320px 날짜별 결과](06-b-320px.png).
- [A 초기 비교 화면](02-a-start.png)은 비교 설정을 접기 전 구현 기록이다. 최종 비교는 07·08을 사용한다.
- 시나리오 날짜: 검수 시 2026-09-14~18, 한국 시간. 실행 시점의 다음 주 월~금으로 독립 생성하며 다른 검토 화면에서 날짜를 바꿔도 영향을 받지 않는다.
- [관련 코드·스타일 원본](baseline/)은 텍스트 사본과 SHA-256 목록으로 보존했다. 전체 앱의 독립 실행 가능한 스냅샷은 아니다. 이후 공통 컴포넌트를 바꾸면 실행 중 A도 바뀔 수 있으므로 재비교 전에 사본과 차이를 확인한다.

## 세 가지 가상 과제

| 상황 | 목표 범위 |
| --- | --- |
| 대부분 가능 | 월~금 09–18시, 매일 12–13시 및 화 15–17시 제외 |
| 드문 가능 시간 | 월 10–12시, 목 14–16시만 포함 |
| 날짜별 차이 | 월·수 09–12시, 화·목 14–18시, 금 09–11시만 포함 |

실제 고객 발화나 실제 회의 데이터가 아니다. 1시간 회의를 묻기 위한 범위 입력 과제이며 참석자의 응답·의사는 포함하지 않는다.

## 이번에 확인한 것

개발 에이전트가 로컬 브라우저와 자동 검사를 수행했다.

- B에서 기본 범위 지정, 여러 날짜 점심 제외, 화요일만 추가 제외 후 첫 과제의 초과·누락이 모두 0분인 것을 확인.
- B에서 빈 범위 시작, 월·목 직접 추가 후 두 번째 과제의 초과·누락 모두 0분 확인. 390×844에서 입력창과 제출 확인.
- B에서 월·수 기본 범위, 화·목 및 금 추가 후 세 번째 과제의 초과·누락 모두 0분 확인. 320×740에서 날짜 체크박스 Space 조작 확인.
- A에서 셀 Space 선택/해제와 되돌리기 확인. 기본 45시간을 그대로 제출하면 첫 과제에서 잘못 포함한 420분이 검출됨.
- 날짜 전체 해제 시 모달 제출 비활성화, Escape 취소 후 범위 유지 확인.
- 320px 버튼의 단어 중간 줄바꿈을 발견해 해당 폭의 패딩·타입 조정. 확인한 320px 결과 화면은 문서 폭 305px로 페이지 가로 넘침 없음. 실제 휴대폰의 터치·OS 선택창과 스크린리더 전 과정은 별도 검증 필요.
- 브라우저 오류·경고 로그 없음. 타입 검사·빌드·린트 통과. 도메인 테스트 52개 통과(추가 3개: 초과·누락·날짜별 범위 판정).
- 기존 시간표 및 직접 입력 컴포넌트의 코드·스타일은 이번 작업 전 사본과 바이트 단위로 동일함.

브라우저에 표시된 수행 시간에는 에이전트 도구 호출과 캡처 대기가 포함됐다. 인간의 입력 속도나 두 안의 성능 비교 자료로 사용하지 않으며 관찰 CSV에도 넣지 않았다. 이번 수정 후 일반 제품 빌드의 산출물은 비교 컴포넌트를 포함하지 않는다. 검토 페이지의 동작은 개발 서버에서 별도로 확인했다.

## 검토 기록 사용법과 한계

1. 안과 과제를 고르고 내용을 읽은 뒤 ‘입력 시작’을 누른다. 시작 이후 비교 설정이 접혀 작업을 가리지 않는다.
2. ‘입력 완료’까지의 경과 시간, 범위 적용 콜백 횟수, 잘못 포함·빠뜨린 분량을 확인한다. B는 기본 범위를 확인하거나 빈 범위 시작을 선택하기 전 완료할 수 없다.
3. 메모를 적고 JSON을 내려받을 수 있다. 데이터는 화면 메모리에만 있으며, 설정 변경·새로고침·다른 검토 화면 이동 시 사라진다. 자동 서버 저장이나 실제 회의 변경은 없다.
4. JSON은 `unclassified-review-run`으로 표시한다. 사용자 관찰·자가 검토·에이전트 점검 중 어떤 실행인지, 기기·입력 수단·도움 여부를 별도 분류한 뒤 연구 자료에 편입한다.

콜백 횟수는 기본 범위 확인과 되돌리기 등을 포함한다. 클릭 수, 실수 수, 인지 부담 측정치가 아니다. 타이머는 중단·탭 전환 시간을 제외하지 않는다. 30분 격자 기반 정답 검사는 이 세 가지 5일 과제에 한정되며 일반 일정 평가기로 사용하지 않는다.

아직 결과 내역별 오류 위치, 수정 횟수의 원인 분류, 자동 세션 축적은 없다. 평가를 위한 UI를 더 늘리기보다 진행자가 관찰 메모로 보완한다.

## 다음 판단

B가 더 짧아 보이는 것만으로 채택하지 않는다. B의 기본 범위 확인 단계와 반복 모달 호출이 오히려 부담일 수 있다. 같은 과제를 두 번 하면 학습 효과가 있으므로 실제 비교에서는 A/B 순서를 교차하고 동형 과제를 준비한다. 도움 없이 정확한 범위를 제출하는지, 결과에 남은 시간의 의미를 설명할 수 있는지 살핀다.

속도가 빨라도 제외해야 할 시간을 포함하면 실패다. 인간 비교 결과가 나오기 전까지 서비스 기본 방식·AI 추가·포트폴리오 효과 수치는 결정하지 않는다.
