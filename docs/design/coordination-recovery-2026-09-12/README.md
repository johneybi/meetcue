# 첫 조율 이후의 재확인 · 2026-09-12

사용자가 D-009의 핵심 세 장면을 빠르게 구현하도록 요청해 만든 로컬 인터랙티브 시안. 원래 제출물과 구분한다. 시장 차별성·사용자 효과·포트폴리오 수록은 아직 판단하지 않는다.

## 문제 정의

첫 후보에 합의하지 못하면, 주최자가 이미 받은 응답을 다시 해석하고 사람마다 재확인해야 한다. 후보에 필요한 확인을 연결하고 기존 응답을 보존해 이 수고를 줄일 수 있을까?

공개 사례에서 유도한 가설이며 직접 사용자 관찰 결과가 아니다. 단순한 일정 투표·확정 기능을 새로 발명했다는 주장이 아니다.

## 열기와 흐름

`npm run dev` 후 `/meetcue/design-review.html?view=recovery`.

1. 화요일은 필수 참석자 수진의 참석 확인, 목요일은 필수 참석자 민수의 일정 변경 동의가 남아 있다. 다른 5명은 각 후보에 가능하다는 가상 데이터다.
2. 주최자는 한 후보를 선택해 해당 사람에게 보일 질문을 확인한다. 요청을 누르면 로컬 대기 상태로 바뀐다. 상단의 ‘수진으로/민수로 응답해 보기’는 시연용 역할 전환이다.
3. 참석자는 그 시간에만 답한다. 수락은 주최자의 확정 버튼을 활성화하고, 거절은 해당 후보를 뒤로 보내 다른 후보의 답을 유지한다.
4. 응답이 늦으면 현재 요청을 취소하고 다른 후보를 확인할 수 있다. 침묵을 거절로 저장하지 않는다.
5. 둘 다 거절하면 새 범위가 필요함을 안내하고 기존 시간 입력 시안으로 연결한다. 돌아오면 두 거절은 유지된다. **새 범위에서 후보 생성·재요청까지는 이번 시안에 연결하지 않았다.**

앱 화면에는 비교 설정·타이머·채점이 없다. ‘바뀐 흐름 보기’에 기존 MeetCue와 메신저로 처리하는 과정의 재구성과 이번 안을 짧게 비교했다. 이는 관찰 데이터가 아니다.

## 구현과 한계

- `CoordinationRecovery`: 주최자·참석자·확정 화면. 기존 Button, MainCard, Badge, Avatar, CalendarDate, TimeRange, Dialog와 표면 토큰 재사용.
- `coordinationRecovery`: 두 후보에 한정한 독립 상태 전이. 미확인·대기·거절은 확정 권한이 아니다. 다른 후보의 답을 덮어쓰지 않는다.
- 밝은 배경과 일관된 얕은 재질, 날짜/시간 → 확인 대상 → 행동 순서. 불가 후보를 다음 행동보다 뒤에 배치한다. 모션 감소 설정 대응.
- 기존 프로덕션 회의·응답 모델에 붙이기 전의 프로토타입이다. 실제 메시지 전송, 계정별 권한, 서버 저장, 다중 기기 동기화, 캘린더 이동은 없다. 새로고침하면 초기화된다.
- 한 번에 한 요청만 진행하는 선택은 불필요한 일정 변경 요청을 줄이려는 가설이다. 직렬 대기로 시간이 늘어날 수 있어 취소 경로를 제공했다. 실제 전송 시스템의 취소/늦은 답/버전 충돌은 구현 범위 밖이다.
- `design-review.html`은 기존과 동일하게 개발 서버 전용이며 프로덕션 빌드의 HTML 진입점에 포함되지 않는다.
