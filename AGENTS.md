# Working agreements

- Work as the primary agent. Do not proactively delegate to subagents.
- Preserve unrelated changes in the working tree.

## Product and design history

The user wants design reasoning, alternatives, and evidence retained during ongoing work so they can later decide what belongs in a portfolio.

- Read `docs/process/README.md` and relevant entries in `docs/process/decision-log.md` before substantial product/design changes.
- For meaningful changes to a flow, visual direction, interaction, or product hypothesis, update the decision log in the same task. Routine fixes do not need individual entries.
- Record the problem, alternatives, decision status, reason, evidence, verification, remaining uncertainty, and portfolio review status. Use `docs/process/entry-template.md` for new entries.
- Preserve existing explorations and before/after evidence. When capturing comparisons, record route, scenario, viewport, and date; explain material differences. Never recreate a historical screen and label it as the original.
- Distinguish user feedback, agent interpretation, public self-reports, code/browser checks, and actual user studies. Do not invent research findings or outcome metrics.
- Keep original submission, post-submission improvements, and proposed work distinct. Record the current date when reconstructing older decisions; use an unknown event date if needed.
- Log recommendations as proposals until adopted. Keep a status history when revising decisions instead of silently rewriting their rationale.
- These records explain decisions; they are not immutable design rules. User instructions take priority. Do not turn documentation or portfolio review into an approval gate. Continue authorized work and record its results.
- Portfolio inclusion is undecided unless the user chooses it. Do not automatically rewrite submission answers or publish case studies from working notes.
